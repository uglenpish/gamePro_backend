# AGENTS.md — Backend

## 1. Область действия

Этот файл применяется к backend-части проекта.

Backend — универсальное ядро игрового сервиса, а не сервер одной конкретной игры.

Основной стек:

- Node.js;
- NestJS;
- TypeScript;
- PostgreSQL;
- Prisma.

Backend отвечает за игровую бизнес-логику, состояние прохождения, контент, условия, эффекты, сохранения, квесты, инвентарь, отношения, боевые механики и API для frontend/редактора.

## 2. Главный принцип backend

NestJS содержит логику.

PostgreSQL хранит данные.

Frontend отображает результат.

Контент описывает правила декларативно.

Не переносить бизнес-логику в:

- SQL;
- Prisma middleware без необходимости;
- Vue;
- JSON-контент в виде исполняемого кода;
- контроллеры.

## 3. TypeScript

Использовать только строгий TypeScript.

Обязательно:

- `strict: true`;
- избегать `any`;
- явно типизировать публичные методы сервисов;
- DTO должны иметь явные типы;
- использовать enum/union/const вместо повторяющихся строковых литералов;
- не использовать необоснованные non-null assertions (`!`);
- не скрывать ошибки типов через цепочки `as unknown as`;
- generic-типы должны иметь понятные ограничения.

Если существует тип доменной сущности, нельзя повторно описывать его вручную в другом модуле без причины.

## 4. NestJS: Controllers

Controller должен быть тонким.

Controller отвечает за:

- получение HTTP-запроса;
- извлечение params/query/body;
- DTO-валидацию;
- передачу данных в application/service слой;
- возврат результата;
- HTTP-specific metadata и decorators.

Controller не должен:

- напрямую обращаться к Prisma;
- реализовывать игровую логику;
- рассчитывать условия и эффекты;
- содержать большие преобразования данных;
- управлять транзакциями;
- содержать сценарную логику конкретной игры.

Плохо:

```ts
@Post()
async create(@Body() dto: CreateSceneDto) {
  const scene = await this.prisma.scene.create(...);
  return scene;
}
```

Хорошо:

```ts
@Post()
async create(@Body() dto: CreateSceneDto): Promise<SceneResponseDto> {
  return this.scenesService.create(dto);
}
```

## 5. NestJS: Services

Service отвечает за бизнес-операцию или отдельную доменную ответственность.

Сервис должен:

- иметь понятную зону ответственности;
- принимать типизированные аргументы;
- возвращать предсказуемый тип;
- скрывать детали реализации от controller;
- переиспользовать общие доменные обработчики.

Не создавать один огромный `GameService`, который делает всё.

Предпочтительно разделять зоны ответственности:

```text
GamesService
ContentVersionsService
ScenesService
ChoicesService
ConditionsService
EffectsService
GameStateService
SavesService
InventoryService
QuestService
RelationsService
CombatService
AssetsService
EditorService
```

Названия окончательно определяются текущей структурой проекта. Не создавать новые слои без необходимости.

## 6. DTO

DTO используется как контракт API.

Правила:

- входные данные валидировать через принятый в проекте механизм;
- не принимать `Record<string, any>` там, где структура известна;
- DTO не должен содержать бизнес-логику;
- DTO API и Prisma model не считать одной и той же сущностью;
- не возвращать Prisma-модель напрямую, если API требует другой контракт;
- секретные поля никогда не попадать в response DTO.

Если формат редактора/движка расширяемый, допускаются JSON-поля, но они должны иметь собственные TypeScript-типы или валидируемые схемы.

## 7. Ошибки

Использовать стандартные NestJS exceptions там, где ошибка соответствует HTTP-смыслу.

Например:

- `BadRequestException`;
- `UnauthorizedException`;
- `ForbiddenException`;
- `NotFoundException`;
- `ConflictException`.

Не возвращать искусственно:

```ts
return { success: false, error: '...' };
```

если исключение является корректным механизмом API.

Не раскрывать пользователю внутренние stack trace, SQL, секреты или внутренние детали инфраструктуры.

## 8. База данных и Prisma

PostgreSQL — основное хранилище.

Prisma используется как основной ORM и источник типизированного доступа к БД.

Структурные изменения БД оформлять через Prisma schema и migrations.

Не менять структуру production-совместимых таблиц вручную в PostgreSQL.

Гибкие структуры допускается хранить в JSONB, если:

- набор полей реально расширяемый;
- по ним не требуется сложная реляционная выборка;
- это условия, эффекты, metadata, content blocks или type-specific data.

Часто фильтруемые и связываемые поля должны оставаться отдельными колонками.

В проекте важно сохранять разделение:

- Identity;
- Content;
- Runtime.

Content и Runtime нельзя смешивать.

## 9. Модель множества игр

Любая игровая сущность должна существовать в контексте конкретной игры и/или версии контента, если это соответствует модели данных.

Нельзя считать, что в системе существует только одна игра.

При проектировании всегда проверять:

- как сущность привязана к `Game`;
- как работает `ContentVersion`;
- могут ли разные игры иметь одинаковые external ID;
- не протекают ли данные одного проекта в другой;
- сохраняется ли совместимость старых сохранений с их версией контента.

## 10. Стабильные идентификаторы

Внутренний ID БД и внешний ID контента — разные понятия.

Обычно:

- внутренний ID — UUID;
- внешний ID — стабильный человекочитаемый идентификатор контента;
- ссылки при импорте резолвятся по external ID;
- после импорта реляционные связи используют внутренний ID.

Нельзя переиспользовать внешний ID опубликованной сущности для другого объекта.

## 11. Условия и эффекты

Условия и эффекты должны реализовываться как расширяемый набор обработчиков.

Примеры условий:

- наличие флага;
- сравнение характеристики;
- наличие предмета;
- состояние квеста;
- отношение с персонажем;
- композиции `all`, `any`, `not`.

Примеры эффектов:

- установить/снять флаг;
- изменить характеристику;
- добавить/удалить предмет;
- изменить отношение;
- начать/завершить/провалить квест;
- изменить стадию;
- изменить runtime-состояние.

Не реализовывать тип эффекта большим растущим `if/else` в случайном сервисе, если уже появляется необходимость в registry/handler-подходе.

Но и не вводить сложную абстракцию заранее, пока в ней нет необходимости.

## 12. Версионирование контента

Опубликованный контент считается immutable.

Новая публикация должна приводить к новой версии контента, если это соответствует текущей модели проекта.

Сохранение игрока должно быть связано с конкретной версией контента.

Нельзя незаметно переключать существующее сохранение на новую версию игры.

Миграция сохранений — отдельная операция.

## 13. API

API должен проектироваться универсально для платформы, а не под конкретный сюжет.

Пример плохого endpoint:

```text
POST /voron/break-seal
```

Предпочтительно:

```text
POST /games/:gameId/saves/:saveId/actions
```

или другой универсальный контракт, соответствующий архитектуре проекта.

Имена маршрутов и DTO должны отражать платформенные сущности.

## 14. Авторизация и безопасность

Секреты и токены не логировать.

Пароли хранить только в виде безопасного хеша.

Не доверять `userId`, `gameId`, `saveId` из клиента без проверки прав доступа.

Для mutation-запросов проверять владение или разрешение пользователя.

Редактор и runtime API могут иметь разные требования к ролям и правам доступа.

## 15. Комментарии и TSDoc

Комментарии писать на русском.

Для сервисов и публичных методов использовать TSDoc, если метод является частью важного контракта или содержит нетривиальную логику.

Пример:

```ts
/**
 * Применяет набор декларативных эффектов к состоянию текущего прохождения.
 * Изменения выполняются последовательно в рамках одной бизнес-операции.
 */
async applyEffects(...): Promise<void> {
  // ...
}
```

Не документировать очевидные getter/setter и простые приватные методы без необходимости.

## 16. Транзакции

Использовать транзакции там, где одна бизнес-операция изменяет несколько связанных сущностей и частичное выполнение недопустимо.

Примеры:

- публикация версии контента;
- применение группы взаимосвязанных эффектов;
- создание нового прохождения с initial state;
- импорт Content Bundle;
- перенос/копирование составной сущности редактора.

Не оборачивать каждый одиночный `findUnique` в транзакцию.

## 17. Импорт и валидация контента

Контент перед сохранением/публикацией должен валидироваться.

Проверять как минимум:

- версию схемы;
- уникальность ID;
- существование ссылок;
- корректность типов сцен;
- валидность условий;
- валидность эффектов;
- корректность target;
- наличие стартовой сцены;
- совместимость с правилами версии контента.

Ошибки импорта должны возвращаться структурированно и быть пригодны для отображения в редакторе.

## 18. Производительность

Не оптимизировать преждевременно.

Но учитывать, что платформа должна поддерживать:

- много игр;
- тысячи сцен;
- большие графы переходов;
- множество сохранений;
- редактор с частыми запросами к контенту.

Избегать N+1-запросов, бесконтрольной загрузки всех сцен игры и передачи огромного runtime-state там, где нужен небольшой projection.

## 19. Проверки после изменений

Если проект содержит соответствующие команды, после изменений backend желательно запускать минимум:

```bash
npm run lint
npm run build
npx prisma validate
```

`prisma validate` нужен только если менялась Prisma schema или связанная конфигурация.

Тесты пока не являются обязательной частью Definition of Done и будут описаны позже.

## 20. Итоговый отчёт агента

После backend-задачи агент должен отдельно указать:

- какие controller/service/module/DTO/Prisma-файлы изменены;
- менялся ли API-контракт;
- менялась ли структура БД;
- нужна ли миграция;
- какие проверки выполнены;
- есть ли влияние на frontend или редактор.
