# 00. Project Philosophy

Документ определяет фундаментальные принципы разработки проекта «Осколки Реальности» и универсального Narrative Engine.

Версия: `0.1.0`

## 1. Цель проекта

Проект состоит из двух независимых продуктов:

1. Игра «Осколки Реальности».
2. Универсальный движок для создания сюжетных игр — Narrative Engine.

Движок разрабатывается под первую игру, но не должен зависеть от её сеттинга. Он должен поддерживать создание других сюжетных проектов без изменения исходного кода.

## 2. Основная идея

Контент не должен зависеть от движка.

Движок не должен зависеть от контента.

Связующим звеном является единая спецификация данных в JSON.

```text
Twine
↓
Parser
↓
JSON
↓
Narrative Engine
↓
Vue Client
```

## 3. Принцип единственной ответственности

Каждая подсистема выполняет только одну задачу.

| Компонент | Ответственность |
| --- | --- |
| Twine | Создание сюжета |
| Parser | Преобразование Twine в JSON |
| JSON | Универсальный формат хранения |
| Backend | Игровая логика |
| Frontend | Отображение |
| PostgreSQL | Хранение данных |

Никакая система не должна выполнять обязанности другой.

## 4. Контент первичен

Проект строится вокруг контента.

Контент включает:

- сцены;
- персонажей;
- квесты;
- предметы;
- диалоги;
- врагов;
- способности;
- игровые события.

Все игровые механики должны обслуживать контент, а не наоборот.

## 5. Движок должен быть универсальным

Движок не должен содержать знаний о мире «Осколков Реальности».

Плохо:

```ts
if (player.hasSeal) {
  // ...
}
```

Хорошо:

```ts
if (player.hasItem(itemId)) {
  // ...
}
```

Или:

```ts
if (player.flags["seal_found"]) {
  // ...
}
```

## 6. Twine используется только как редактор

Twine — инструмент сценариста.

Он предназначен для:

- построения графа;
- написания текста;
- проектирования ветвлений.

Twine не является игровым движком.

В Twine запрещается реализовывать:

- боевую систему;
- расчёт характеристик;
- сохранения;
- инвентарь;
- анимации;
- пользовательский интерфейс.

## 7. JSON — единственный источник данных

После импорта в движок Twine больше не используется.

Все игровые объекты представлены в JSON:

- Scene;
- Choice;
- Character;
- Quest;
- Item;
- Enemy;
- Ability.

Любой объект должен быть сериализуем.

## 8. Сцена — минимальная единица повествования

Каждая сцена должна иметь одну основную цель.

Подходящие примеры:

- пробуждение;
- диалог;
- осмотр комнаты;
- засада.

Не следует объединять несколько смысловых событий в одну сцену без необходимости.

## 9. Ветки должны объединяться

Не нужно создавать множество почти одинаковых сцен.

Если разные варианты выбора приводят к одному событию, предпочтительно использовать общую сцену. Различия внутри сцены должны определяться состоянием игрока.

Плохо:

```text
scene_after_choice_a
scene_after_choice_b
scene_after_choice_c
```

Хорошо:

```text
common_scene
```

А различия описываются условиями:

```text
if awareness >= 10
```

## 10. Игровое состояние отделено от сцены

Сцена не хранит состояние игрока.

Состояние хранится отдельно:

- health;
- sanity;
- inventory;
- flags;
- quests;
- relations.

Сцена только читает состояние через условия и изменяет его через эффекты.

## 11. Идентификаторы неизменяемы

Каждый объект имеет постоянный идентификатор.

Пример:

```text
l1_001_apartment_wakeup
```

ID никогда не меняется, даже если меняется текст сцены.

## 12. Человекочитаемые данные отделены от технических

Плохо:

```text
scene_15
```

Хорошо:

```text
l1_001_apartment_wakeup
```

Название должно объяснять назначение сцены.

## 13. Логика должна быть декларативной

Контент описывает, что должно произойти.

Движок решает, как это выполнить.

Пример контента:

```json
{
  "effect": "add_item",
  "itemId": "seal_fragment"
}
```

Пример реализации в движке:

```ts
InventoryService.addItem(playerId, itemId);
```

## 14. Повторное использование

Любая сцена может использоваться несколько раз.

Примеры:

- осмотреться;
- журнал;
- карта;
- универсальный магазин.

Для этого используется механизм возврата.

```text
RETURN
```

## 15. Масштабируемость

Проект должен поддерживать:

- тысячи сцен;
- сотни NPC;
- десятки историй;
- множество игровых миров.

Это не должно требовать изменения архитектуры.

## 16. AI является помощником автора

AI помогает создавать:

- сцены;
- диалоги;
- квесты;
- описания;
- NPC.

AI обязан соблюдать спецификацию проекта.

## 17. Правила для AI

AI обязан:

- использовать утверждённые типы сцен;
- использовать утверждённые схемы JSON;
- соблюдать систему именования;
- объединять ветви при возможности;
- не создавать дублирующиеся сцены;
- использовать единый DSL;
- не помещать игровую логику в Twine.

## 18. Принцип расширяемости

Добавление новой механики не должно требовать изменения существующих сцен.

Новая функциональность должна добавляться через:

- новые типы эффектов;
- новые условия;
- новые обработчики.

## 19. Принцип обратной совместимости

После публикации спецификации:

- существующие JSON должны продолжать работать;
- новые возможности не должны ломать старые истории.

## 20. Итоговая архитектура

```text
Автор
↓
Twine
↓
Parser
↓
JSON
↓
Import
↓
PostgreSQL
↓
Narrative Engine (NestJS)
↓
Vue Client
↓
Игрок
```
