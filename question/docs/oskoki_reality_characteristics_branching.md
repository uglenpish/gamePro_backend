# «Осколки реальности»: характеристики героя и система ветвления

## Назначение документа

Этот документ описывает психологические характеристики Ворона, систему сюжетных флагов, коллекций, отношений и правил ветвления для игры «Осколки реальности».

Twine используется только как графический редактор сцен и связей между ними. Основная логика игры должна храниться в структурированных данных и исполняться собственным движком на Vue 3, Nest.js и PostgreSQL.

Рекомендуемая схема:

```text
Twine / Twee
    ↓
Импортёр Nest.js
    ↓
Проверка структуры сцен, условий и эффектов
    ↓
PostgreSQL
    ↓
Vue 3 отображает сцену и доступные выборы
```

---

# 1. Общий принцип развития героя

«Осколки реальности» — психологический хоррор, а не классическая RPG. Поэтому Ворону не нужны традиционные параметры вроде силы, ловкости, выносливости и урона.

Игрок не прокачивает героя как бойца. Своими решениями он постепенно формирует его личность, мировоззрение и отношение к потустороннему миру.

Характеристики должны влиять на:

- доступные варианты ответа;
- способы решения конфликтов;
- восприятие реальности;
- доступные знания и наблюдения;
- реакцию людей и существ промежуточных слоёв;
- возможность мирного или жестокого прохождения сцены;
- доверие союзников;
- изменение текста одной и той же сцены;
- доступ к отдельным сюжетным веткам;
- финальный образ Ворона и концовку.

Игроку необязательно показывать точные числа. Значения могут оставаться скрытыми и проявляться через сюжетные последствия.

---

# 2. Основные психологические характеристики

Рекомендуется оставить пять основных характеристик. Этого достаточно для глубокого ветвления, но система не станет перегруженной.

## 2.1. Решимость — `resolve`

Показывает готовность Ворона действовать, брать ответственность и продолжать путь под давлением.

Высокая решимость позволяет:

- не отступать перед опасной сущностью;
- удерживать или восстанавливать печати;
- принимать тяжёлые решения;
- сопротивляться запугиванию;
- вести за собой союзников;
- открывать прямые и рискованные варианты действий.

Низкая решимость может:

- открывать осторожные пути;
- усиливать стремление избежать конфликта;
- вызывать сомнения;
- закрывать некоторые жёсткие решения;
- делать героя более зависимым от поддержки союзников.

Пример изменения:

```json
{
  "op": "addStat",
  "stat": "resolve",
  "value": 1
}
```

---

## 2.2. Эмпатия — `empathy`

Показывает способность Ворона понимать людей, одержимых, существ промежуточных слоёв и даже отдельных прислужников демонов.

Высокая эмпатия позволяет:

- видеть мотивы противника;
- замечать страх или сомнение;
- договариваться;
- спасать одержимых вместо их уничтожения;
- приобретать союзников;
- получать признание лояльных существ;
- открывать мирные или компромиссные решения.

Низкая эмпатия может:

- закрывать доверительные диалоги;
- усиливать холодность и жестокость;
- упрощать решения через уничтожение;
- вызывать страх или отвращение у союзников;
- делать Ворона эффективным, но одиноким хранителем.

Пример изменения:

```json
{
  "op": "addStat",
  "stat": "empathy",
  "value": -2
}
```

---

## 2.3. Устойчивость восприятия — `stability`

Показывает способность Ворона отличать реальность от иллюзий, сохранять внутреннюю целостность и сопротивляться воздействию слоёв.

Высокая устойчивость позволяет:

- распознавать ложные образы;
- замечать подмену людей;
- видеть настоящие символы и проходы;
- сопротивляться внушению;
- сохранять точность воспоминаний;
- отличать голос союзника от голоса сущности.

Низкая устойчивость может:

- менять описание сцен;
- добавлять ложные варианты выбора;
- скрывать настоящие выходы;
- искажать имена персонажей;
- вызывать противоречивые воспоминания;
- делать часть интерфейса ненадёжной.

Для психологического хоррора эта характеристика особенно важна. Она не должна быть обычной полоской «психики». Лучше использовать её как скрытый параметр, влияющий на восприятие текста и событий.

Пример изменения:

```json
{
  "op": "addStat",
  "stat": "stability",
  "value": -1
}
```

---

## 2.4. Скверна — `corruption`

Показывает степень влияния потустороннего мира на Ворона.

Скверна не должна быть только наказанием. Она может давать силу, знания и новые пути, но постепенно менять героя.

Высокая скверна может:

- открывать демонические способности;
- позволять видеть скрытые проходы нижних слоёв;
- менять отношение демонов к Ворону;
- давать возможность использовать запрещённые печати;
- усиливать страх людей и союзников;
- приводить к альтернативным концовкам;
- постепенно менять речь, внешний образ и способы мышления героя.

Низкая скверна позволяет:

- сохранять доверие хранителей и людей;
- легче использовать защитные печати;
- сопротивляться демоническим сделкам;
- сохранять связь с человеческим миром.

Пример изменения:

```json
{
  "op": "addStat",
  "stat": "corruption",
  "value": 2
}
```

---

## 2.5. Знание печатей — `sealKnowledge`

Показывает не общую эрудицию, а понимание устройства печатей, слоёв, ритуалов и законов перехода между мирами.

Высокое значение позволяет:

- распознавать тип печати;
- находить слабое место ритуала;
- замечать фальшивые символы;
- восстанавливать печать без жертвы;
- понимать устройство конкретного слоя;
- открывать специальные реплики в разговорах с хранителями и древними существами;
- заменять прямой бой ритуальным решением.

Знание лучше повышать не обычным опытом, а через найденные записи, изученные символы, воспоминания и разговоры с персонажами.

Пример изменения:

```json
{
  "op": "addStat",
  "stat": "sealKnowledge",
  "value": 1
}
```

# 3. Что не следует делать характеристикой

Некоторые данные лучше хранить отдельно.

## 3.1. Память

Память лучше не делать обычным числом.

Вместо:

```json
{
  "memory": 7
}
```

лучше хранить конкретные найденные фрагменты:

```json
{
  "memories": [
    "memory.raven.first_oath",
    "memory.fifth_layer",
    "memory.previous_keeper"
  ]
}
```

Так сюжет сможет проверять не количество воспоминаний, а их содержание.

Пример условия:

```json
{
  "op": "hasMemory",
  "memory": "memory.raven.first_oath"
}
```

## 3.2. Инвентарь

Предметы должны храниться отдельной коллекцией:

```json
{
  "items": [
    "item.seal_fragment",
    "item.ritual_knife"
  ]
}
```

## 3.3. Энциклопедия и знания о существах

Открытые записи также лучше хранить отдельной коллекцией:

```json
{
  "codexEntries": [
    "creature.echo_walker",
    "seal.blood_mark"
  ]
}
```

## 3.4. Сюжетные события

Факт произошедшего должен храниться как флаг, а не как характеристика.

Например:

```json
{
  "flags": {
    "phone.answered": true,
    "cultist.firstSpared": false,
    "seal.firstBroken": true,
    "anna.rescued": true
  }
}
```

# 4. Разделение данных игрока

Состояние прохождения рекомендуется разделить на четыре части.

## 4.1. Характеристики — каким становится Ворон

```json
{
  "stats": {
    "resolve": 0,
    "empathy": 0,
    "stability": 0,
    "corruption": 0,
    "sealKnowledge": 0
  }
}
```

## 4.2. Флаги — что произошло

```json
{
  "flags": {
    "phone.answered": true,
    "anna.rescued": false,
    "seal.firstBroken": true
  }
}
```

## 4.3. Коллекции — что найдено или изучено

```json
{
  "items": ["item.seal_fragment"],
  "memories": ["memory.first_oath"],
  "codexEntries": ["creature.echo_walker"]
}
```

## 4.4. Отношения — кто и насколько доверяет герою

```json
{
  "relations": {
    "anna": 3,
    "keeper.aron": -1,
    "wanderer.nox": 5
  }
}
```

Это разделение позволяет легко писать и проверять условия.

# 5. Как записывать изменения характеристик

Не следует записывать итоговое значение прямо в сцене:

```json
{
  "empathy": 7
}
```

Сцена должна содержать операцию, которую движок применяет к текущему состоянию игрока.

## 5.1. Увеличение или уменьшение

```json
{
  "op": "addStat",
  "stat": "empathy",
  "value": 2
}
```

```json
{
  "op": "addStat",
  "stat": "stability",
  "value": -1
}
```

## 5.2. Установка точного значения

Используется редко:

```json
{
  "op": "setStat",
  "stat": "corruption",
  "value": 0
}
```

## 5.3. Ограничение диапазона

Для характеристик рекомендуется использовать диапазон, например от `-10` до `10` или от `0` до `100`.

Для сюжетной игры удобнее небольшой диапазон:

```text
-10 ... 10
```

Пример интерпретации:

```text
-10 ... -6 — выраженно низкое значение
 -5 ... -2 — низкое значение
 -1 ...  1 — нейтральное значение
  2 ...  5 — высокое значение
  6 ... 10 — выраженно высокое значение
```

При применении эффекта движок должен ограничивать значение:

```ts
newValue = Math.max(-10, Math.min(10, oldValue + delta));
```

# 6. Как записывать сюжетные флаги

Рекомендуется использовать плоскую карту флагов со строковыми ключами:

```json
{
  "phone.answered": true,
  "seal.firstBroken": false,
  "anna.rescued": true
}
```

Такой формат удобен для универсального интерпретатора:

```ts
flags["phone.answered"] === true
```

## 6.1. Установка флага

```json
{
  "op": "setFlag",
  "key": "phone.answered",
  "value": true
}
```

## 6.2. Проверка флага

```json
{
  "op": "flagEquals",
  "key": "phone.answered",
  "value": true
}
```

## 6.3. Правила именования

Флаг должен описывать конкретный факт:

```text
phone.answered
cultist.firstSpared
seal.firstBroken
anna.rescued
layer5.gatewayOpened
```

Неудачные названия:

```text
goodChoice
badEnding
importantFlag
state1
```

Имя должно быть понятно без чтения всей сцены.

# 7. Система условий

Все условия рекомендуется представлять в виде объектов с полем `op`.

## 7.1. Проверка флага

```json
{
  "op": "flagEquals",
  "key": "anna.rescued",
  "value": true
}
```

## 7.2. Проверка характеристики

Больше или равно:

```json
{
  "op": "statGte",
  "stat": "empathy",
  "value": 5
}
```

Меньше или равно:

```json
{
  "op": "statLte",
  "stat": "stability",
  "value": -3
}
```

Строго меньше:

```json
{
  "op": "statLt",
  "stat": "sealKnowledge",
  "value": 4
}
```

## 7.3. Проверка предмета

```json
{
  "op": "hasItem",
  "item": "item.seal_key"
}
```

## 7.4. Проверка воспоминания

```json
{
  "op": "hasMemory",
  "memory": "memory.raven.first_oath"
}
```

## 7.5. Проверка отношения

```json
{
  "op": "relationGte",
  "character": "anna",
  "value": 4
}
```

## 7.6. Проверка текущего слоя

```json
{
  "op": "currentLayerEquals",
  "value": 5
}
```

# 8. Сложные условия: AND, OR и NOT

## 8.1. AND

Все вложенные условия должны быть истинными:

```json
{
  "op": "and",
  "conditions": [
    {
      "op": "flagEquals",
      "key": "anna.rescued",
      "value": true
    },
    {
      "op": "statGte",
      "stat": "empathy",
      "value": 5
    }
  ]
}
```

## 8.2. OR

Достаточно одного истинного условия:

```json
{
  "op": "or",
  "conditions": [
    {
      "op": "hasItem",
      "item": "item.seal_key"
    },
    {
      "op": "statGte",
      "stat": "sealKnowledge",
      "value": 7
    }
  ]
}
```

## 8.3. NOT

Инвертирует условие:

```json
{
  "op": "not",
  "condition": {
    "op": "flagEquals",
    "key": "seal.firstBroken",
    "value": true
  }
}
```

# 9. Как делать аналог if / else

Так как Twine используется только как редактор графа, логику `if / else` лучше не писать через SugarCube.

Вместо этого можно использовать два подхода.

## 9.1. Разные переходы с противоположными условиями

```json
[
  {
    "id": "recognize_symbol",
    "text": "Вы узнаёте символ Хранителей",
    "targetSceneId": "seal.recognized",
    "conditions": [
      {
        "op": "statGte",
        "stat": "sealKnowledge",
        "value": 5
      }
    ]
  },
  {
    "id": "symbol_unknown",
    "text": "Символ вам незнаком",
    "targetSceneId": "seal.unknown",
    "conditions": [
      {
        "op": "statLt",
        "stat": "sealKnowledge",
        "value": 5
      }
    ]
  }
]
```

## 9.2. Варианты текста одной сцены

```json
{
  "contentVariants": [
    {
      "priority": 100,
      "conditions": [
        {
          "op": "statLte",
          "stat": "stability",
          "value": -3
        }
      ],
      "text": "Стены дышат. Телефон шепчет вашим голосом."
    },
    {
      "priority": 0,
      "conditions": [],
      "text": "Комната выглядит обычной, если не считать звонящего телефона."
    }
  ]
}
```

Движок проверяет варианты по убыванию `priority` и выбирает первый подходящий.

# 10. Как характеристики должны влиять на сюжет

Характеристики не должны постоянно создавать полностью отдельные сюжетные линии. Иначе количество сцен быстро станет неконтролируемым.

Лучше разделить влияние на четыре уровня.

## 10.1. Изменение текста

Одна и та же сцена описывается по-разному.

Пример:

- высокая устойчивость — Ворон видит настоящий коридор;
- низкая устойчивость — коридор кажется бесконечным;
- высокая скверна — он замечает скрытый знак демона.

## 10.2. Изменение доступных выборов

Пример:

- высокая эмпатия открывает попытку успокоить одержимого;
- высокое знание печатей открывает ритуал изгнания;
- высокая скверна открывает поглощение сущности;
- высокая решимость открывает прямое сопротивление.

## 10.3. Изменение последствий одного выбора

Одинаковый выбор может привести к разным результатам.

Например, Ворон пытается восстановить печать:

- при высоком `sealKnowledge` печать восстановлена безопасно;
- при среднем значении Ворон получает скверну;
- при низком значении печать ломается окончательно.

## 10.4. Переход в отдельную сюжетную ветку

Отдельную ветку стоит создавать только для важных поворотных моментов:

- союз с конкретной фракцией;
- гибель или спасение ключевого персонажа;
- разрушение крупной печати;
- принятие демонической силы;
- раскрытие важного воспоминания;
- переход к одной из финальных линий.

# 11. Флаги и характеристики должны работать вместе

Флаги отвечают на вопрос: **что произошло?**

Характеристики отвечают на вопрос: **каким стал Ворон?**

Пример условия для особой сцены:

```json
{
  "op": "and",
  "conditions": [
    {
      "op": "flagEquals",
      "key": "anna.rescued",
      "value": true
    },
    {
      "op": "statGte",
      "stat": "empathy",
      "value": 5
    },
    {
      "op": "relationGte",
      "character": "anna",
      "value": 4
    }
  ]
}
```

Такой подход делает ветвление логичным. Игрок должен не только спасти Анну, но и заслужить её доверие.

---

# 12. Система отношений

Каждый важный персонаж может иметь числовой показатель отношения к Ворону.

```json
{
  "relations": {
    "anna": 0,
    "keeper.aron": 0,
    "wanderer.nox": 0
  }
}
```

Изменение отношения:

```json
{
  "op": "addRelation",
  "character": "anna",
  "value": 2
}
```

Проверка:

```json
{
  "op": "relationGte",
  "character": "anna",
  "value": 4
}
```

Отношения должны влиять на:

- откровенность диалогов;
- помощь в сложных сценах;
- готовность персонажа сопровождать героя;
- предоставление знаний или предметов;
- предательство;
- судьбу персонажа в финале.

# 13. Архетипы Ворона

Игрок не выбирает класс в начале. Архетип формируется из решений.

## Хранитель

Пример условий:

```text
resolve высокий
empathy высокая
corruption низкая
```

Такой Ворон защищает печати и старается сохранить жизни.

## Охотник

```text
resolve высокий
empathy низкая
corruption средняя или высокая
```

Он эффективен, жесток и всё чаще воспринимает существ как цели.

## Искатель истины

```text
sealKnowledge высокий
найдено много воспоминаний
решимость средняя
```

Он стремится раскрыть происхождение печатей и настоящую роль хранителей.

## Падший хранитель

```text
corruption высокая
stability низкая
несколько ключевых печатей разрушены
```

Он может считать, что контролирует силу, хотя постепенно становится частью угрозы.

Архетип можно вычислять динамически или определять только перед финалом.

# 15. Как оформлять passage в Twine

Один passage должен соответствовать одной сцене.

Название passage используется как уникальный идентификатор:

```text
apartment.wakeup
apartment.answer_phone
apartment.ignore_phone
layer2.entrance
seal.first_encounter
```

Внутри passage можно использовать конфигурационный блок и обычные ссылки Twine.

```text
@config
{
  "id": "apartment.wakeup",
  "type": "scene",
  "location": "apartment",
  "layer": 1,
  "media": {
    "background": "apartment_morning.webp",
    "music": "phone_loop.ogg"
  },
  "choices": {
    "apartment.answer_phone": {
      "id": "answer_phone",
      "conditions": [],
      "effects": [
        {
          "op": "setFlag",
          "key": "phone.answered",
          "value": true
        },
        {
          "op": "addStat",
          "stat": "resolve",
          "value": 1
        }
      ]
    },
    "apartment.ignore_phone": {
      "id": "ignore_phone",
      "conditions": [],
      "effects": [
        {
          "op": "setFlag",
          "key": "phone.ignored",
          "value": true
        }
      ]
    }
  }
}
@endconfig

Вы просыпаетесь в своей квартире от телефонного звонка.

Телефон вибрирует на тумбочке.

[[Взять трубку->apartment.answer_phone]]
[[Сбросить звонок->apartment.ignore_phone]]
```

Twine использует ссылки для построения графа, а импортёр Nest.js извлекает JSON между `@config` и `@endconfig`.

# 18. Как не допустить взрыва количества веток

Главная опасность — создавать отдельную сцену для каждого небольшого изменения характеристик.

Лучше применять правило:

- небольшие изменения влияют на текст;
- средние изменения влияют на доступные выборы;
- важные комбинации влияют на результат сцены;
- отдельные сюжетные ветки создаются только для крупных решений.

Пример:

```text
Низкая устойчивость
→ другой текст комнаты

Высокая эмпатия
→ дополнительная реплика

Высокое знание печатей
→ альтернативное решение конфликта

Спасение ключевого персонажа
→ отдельная сюжетная ветка
```

# 19. Скрытые и видимые характеристики

Для этой игры рекомендуется не показывать точные значения основных характеристик.

Вместо числа:

```text
Эмпатия: 7
```

можно показывать состояния:

```text
Эмпатия: высокая
Устойчивость: нарушена
Скверна: заметная
```

Или вообще не показывать их напрямую. Игрок понимает изменения по:

- репликам Ворона;
- реакции союзников;
- изменению текста;
- доступным выборам;
- визуальным эффектам;
- поведению интерфейса.

Точные числа полезны движку, но необязательно игроку.

# 21. Главный принцип проектирования

Система должна всегда различать:

```text
Флаги         → что произошло
Характеристики → каким стал Ворон
Отношения      → кто ему доверяет
Предметы       → что он получил
Воспоминания   → что он вспомнил
Знания         → что он изучил
```

Twine отвечает за удобное визуальное построение графа сцен.

Nest.js отвечает за:

- импорт сцен;
- проверку условий;
- применение эффектов;
- сохранение состояния;
- выбор доступных вариантов;
- выбор подходящего варианта текста;
- обработку ветвлений.

Vue 3 отвечает за:

- отображение текста;
- картинки и фон;
- анимации;
- звук;
- варианты выбора;
- визуальные искажения при низкой устойчивости или высокой скверне.

Такой подход позволит использовать один движок не только для «Осколков реальности», но и для других текстовых квестов.
